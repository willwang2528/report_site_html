# VLM-Fuzz：把弹窗建模为可回放的临时状态

- 日期：2026-08-22
- 论文：[VLM-Fuzz: Vision Language Model Assisted Recursive Depth-First Search Exploration for Effective GUI Testing of Android Apps](https://doi.org/10.1007/s10664-026-10816-4)
- 正式版本：*Empirical Software Engineering* 31, Article 76，2026-02-13
- 预印本：[arXiv:2504.11675](https://arxiv.org/abs/2504.11675)
- 代码：[biniamf/VLM-Fuzz](https://github.com/biniamf/VLM-Fuzz)
- 定位：覆盖率导向的 Android 黑盒 GUI 测试；弹窗恢复是总体系统的一个状态搜索子机制

## 1. 一句话结论

VLM-Fuzz 解决的是测试器进入 Dialog、Popup Menu 等临时界面后丢失宿主搜索位置的问题：它把覆盖层建模为有独立 UI 树、宿主关系和进入路径的临时状态，遍历其中的动作；当 OK、Cancel 等操作关闭弹窗后，再比较宿主 Activity 是否改变，决定创建新状态或从触发弹窗的控件继续执行。

> 论文证明完整系统提高了代码覆盖率，但没有弹窗专项成功率，也没有把弹窗机制单独消融。因此不能把总体覆盖率写成“弹窗处理成功率”。

## 2. 为什么普通 DFS 会被弹窗打断

普通深度优先搜索假设，新页面探索完后可以返回父页面。但 Android 覆盖层同时具备三个特征：

1. 它覆盖在当前 Activity 上，却可能有独立的 UI hierarchy XML；
2. 点击任一选项便可能立即关闭、修改宿主、切换 Activity，甚至退出应用；
3. 覆盖层关闭后，视觉上回到旧页面，不代表宿主状态和 DFS 游标没有变化。

![三类复杂 Android GUI](/research-mobile/popup-assets/vlm-fuzz/fig-2-complex-gui.png)

图 2 的左图是本文弹窗机制的核心场景：动态菜单覆盖宿主 GUI。中图需要语义有效输入，右图需要特定动作序列；后两类问题由按需 VLM 输入生成辅助处理。

## 3. 总体方法

系统不是“让 GPT-4o 从头到尾操作 App”，而是一个混合测试框架：

1. 从 Manifest 提取公开 Activity、Intent Filter 和深链，以显式 Intent 从多个入口启动组件；
2. 按普通交互控件数与菜单可达控件数，为每个 Activity 分配 60 分钟总预算的一部分；
3. 含文本输入控件的页面调用 GPT-4o 生成动作序列，并与控件静态属性交叉校验；
4. 无文本输入页面按启发式顺序执行点击、长按、滚动和菜单动作；
5. 每次动作后比较 Activity 与 UI 树，递归探索新状态并保存转移记录。

![VLM-Fuzz 总体架构](/research-mobile/popup-assets/vlm-fuzz/fig-3-architecture.png)

组件 `i` 的预算比例为：

```text
BudgetRatio_i = (w_i + 4m_i) / Σ(j∈S)(w_j + 4m_j)
B_i = BudgetRatio_i × B_total
```

`w_i` 是普通交互控件数，`m_i` 是菜单可达控件数。菜单按 4 倍计入是经验启发式，不是训练得到或经独立消融验证的最优参数。

## 4. 弹窗递归探索机制

### 4.1 识别临时状态

执行动作后，如果 Activity 没有变化，系统比较动作前后的交互控件集合。若出现新的 GUI 层，再将布局包围盒与屏幕比较：只要任一边界间距超过经验阈值 **150 像素**，就分类为 Popup。

Dialog、Popup 和 Spinner 随后被标记为 transient state。进入临时状态时，不增加底层宿主 Activity 的访问次数；否则一个含多个弹窗的 Activity 很快就会达到访问阈值 $\tau=2$，被测试器过早终止。

### 4.2 Dialog 与 Popup：遍历、关闭、比较宿主

系统尽量执行弹窗中的全部尚未探索动作。某个 OK、Cancel 或菜单项关闭弹窗后，它重新读取宿主 UI 树：

| 关闭后的宿主 | 下一步 |
|---|---|
| 宿主 UI 已改变 | 把变化后的布局创建为新状态并递归探索 |
| 宿主 UI 未改变 | 回到触发弹窗的控件，从其后继续原 DFS |

### 4.3 Spinner：只随机选择一个条目

Spinner 选择任一条目都会立即关闭下拉层。为避免每次选择后反复重开形成循环，VLM-Fuzz 只随机选择一个条目、不回溯，再从宿主的 Spinner 控件继续。这是提高终止性的工程折中，不是完整的下拉选项遍历。

### 4.4 路径重放：找回未完成分支

若弹窗中的某个动作在其余控件尚未遍历时就切走页面，系统保存进入该状态的动作序列。完成新状态探索后，它重放此前路径，跳过最后一个导致离开的动作，再执行旧状态中剩余控件。若重放不能回到旧状态，就把该 GUI 视为永久改变并结束该分支。

![宿主 Activity 与 Popup 之间的递归状态路径](/research-mobile/popup-assets/vlm-fuzz/fig-7-popup-state-space.png)

这张图展示 TimerActivity、Preferences 与 InstrumentedActivity 的宿主状态和多个 Popup 状态之间的往返。真正可复用的设计不是固定按 Back，而是“宿主指纹 + 触发控件 + 转移记录 + 重放后验证”。

## 5. 关键结果

AndroTest 原有 66 个插桩应用，排除 7 个无法运行或插桩的应用后使用 59 个。每个工具对每个应用运行 60 分钟并重复 5 次。

| 覆盖率 | DeepGUI | APE | VLM-Fuzz | 相对 APE 的数值差 |
|---|---:|---:|---:|---:|
| 类 | 57.8% | 59.5% | **68.5%** | +9.0 个百分点 |
| 方法 | 48.0% | 49.5% | **53.2%** | +3.7 个百分点 |
| 行 | 43.7% | 44.4% | **46.5%** | +2.1 个百分点 |

![覆盖率主结果](/research-mobile/popup-assets/vlm-fuzz/fig-9-coverage.png)

类和方法覆盖率相对两个基线达到论文设定的显著性阈值。行覆盖率相对 APE 的 $p=0.037$，相对 DeepGUI 的 $p=0.072$；后一项不能宣称显著。

### VLM 和多入口并非唯一原因

- 59 个应用中有 13 个没有调用 VLM，其中 9 个只靠启发式便超过 APE 的行覆盖率；
- VLM 消融只从 46 个需要模型的应用中随机选了 5 个，完整方法相对无 VLM 版本的平均行覆盖率相对提升为 5.28%；
- 单入口变体与 APE 的平均类覆盖率同为 61.5%，行覆盖率为 45.9% 对 45.1%。

因此，论文支持的是多入口、预算、语义输入和递归状态恢复的组合收益，不能把全部优势只归因于 GPT-4o 或弹窗处理。

### 现实应用崩溃

正式期刊版在 80 个 2024 年更新的 Google Play 应用上运行后，由两名作者结合日志和截图人工排除非真实用户路径异常，最终确认 **12 个应用中的 52 个独特崩溃**，涉及 23 种异常类型。APE 找到 14 个，二者重合 4 个。

Themis 中两个工具都触发 3 个已记录缺陷；对未记录崩溃，VLM-Fuzz 为 140 个、APE 为 11 个，重合 5 个。该结果很大一部分来自多入口绕过失效首页，但 Themis 官方脚本本身只有 9/79 成功，解释时必须保留基准老化边界。

## 6. 弹窗问题的严格边界

1. **没有弹窗专项成功率。** 论文没有报告 Popup 检测精度、关闭后恢复率、重放成功率或弹窗机制独立消融。
2. **不是随机广告处理器。** 主要处理应用内部可访问的 Dialog、Popup Menu、Spinner 和相关框架弹窗，不专门覆盖随机广告或任意跨应用覆盖层。
3. **不是用户任务动作选择器。** 为提高代码覆盖率，测试器会尝试多个尚未探索的动作；它不负责选择最符合用户意图的唯一 OK、Cancel 或 Allow。
4. **150 像素是经验阈值。** 规则可能漏掉全屏 Dialog，也可能误判大边距或边到边布局。
5. **Spinner 探索不完整。** 每次只随机选一个条目，明确牺牲选项覆盖来避免循环。
6. **动作空间有限。** VLM-Fuzz 只支持 7 类 GUI 事件，APE 支持 33 类；拖拽、缩放和部分硬件键事件没有覆盖。
7. **VLM 证据有限。** 模型选择只有 10 张截图和一名评判者，消融只有 5 个应用；GPT-4o 还存在成本、专有模型漂移和复现风险。
8. **只验证 Android。** 结果不能直接外推到 iOS、移动 Web 或安全验证弹窗。

## 7. 对移动端弹窗处理的复用建议

一个可恢复弹窗处理器至少应保存：

```text
宿主状态指纹
  + 触发弹窗的控件
  + 弹窗自己的控件集合
  + 进入弹窗的动作序列
  + 尚未探索的动作集合
  + 关闭后的宿主差分
```

评估时还应新增弹窗检测精度、宿主恢复率、重放成功率、弹窗分支覆盖率与不可逆副作用率。若系统面向真实用户任务，则必须把“测试模式的多动作覆盖”与“任务模式的单动作、安全决策”分开；权限、支付、删除、身份验证、CAPTCHA 和平台安全控制不能沿用覆盖率优先策略。

## 8. 精读判断

这篇论文对弹窗问题最强的贡献是状态建模：临时覆盖层不会污染宿主访问计数，关闭后会核对宿主是否改变，未完成分支能通过动作序列重放恢复。最弱的地方也很明确：论文只证明完整 GUI 测试器有效，没有测量弹窗子机制的独立增益。

所以，若把它放进移动端弹窗方案库，正确标签应是：**覆盖率导向测试框架中的递归弹窗恢复机制**，而不是“通用弹窗自动决策方案”。
