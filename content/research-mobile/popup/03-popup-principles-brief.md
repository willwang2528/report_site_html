# “允许”以完成任务，却在无意中授予过多权限

- 日期：2026-08-22
- 论文：[*"Allow" to Achieve, Over-Privileged Inadvertently*](https://arxiv.org/abs/2608.04755)
- 版本：arXiv v1，2026-08-05
- 定位：移动 GUI Agent 权限决策的实证研究与基准

## 1. 一句话结论

移动 GUI Agent 很容易把“完成当前任务”误当成“应该同意当前弹窗”：即使权限与任务无关，只要请求者看起来与任务相关，模型也可能点击 **Allow**。论文将这种能力定义为 **Permission Literacy（权限素养）**，并证明单靠提示词虽然能减少越权授权，却常以大量拒绝必要权限为代价。

> 真正需要优化的不是“拒绝率”，而是“最小充分授权”：该给的给，不该给的拒绝或延后。

## 2. 论文在研究什么

作者把弹窗权限决策分成四级：

| 等级 | 与当前任务的关系 | 正确动作 |
|---|---|---|
| L1 | 完成任务所必需 | Allow |
| L2 | 弱相关，但并非当前步骤必需 | Deny / Defer |
| L3 | 与任务无关 | Deny / Defer |
| L4 | 明显过度、风险更高 | Deny / Defer |

“权限素养”不是见到风险就一律拒绝，而是让 Agent 根据**任务、请求者、权限类型和当前步骤**判断最小必要授权。

三名专家对 24 个权限场景进行校验：二元“允许/拒绝”标注的 Fleiss κ 为 **0.869**、两两一致率 **95.8%**；四级细分的 κ 为 **0.574**、两两一致率 **75.0%**。这说明二元政策相当稳定，但精细等级仍有边界案例，尤其是通讯录相关 L1。

![四级权限分类与任务示例](/research-mobile/popup-assets/2608.04755/table-1.png)

## 3. 实验是怎样做的

实验基于 AndroidLab，覆盖 Calendar、Clock、Contacts、PiMusic、Zoom 五个 App：

- 67 个独立任务；
- 每个任务注入 L1–L4 四级权限弹窗，共 268 个条件；
- 测试 Doubao、Gemini、GPT-5、Qwen3-VL 四个模型；
- 主实验共 **1,072 次**运行；
- 模型同时接收标注截图与 UI 树，弹窗在第三次交互时注入；
- 温度设为 0，以减少采样噪声。

论文的 Grant Rate 只统计模型明确点击 Allow 的情况。拒绝、返回桌面、无效动作或转向其他界面都保留在分母中；API 故障才排除。这个定义比只看成功轨迹更严格，但合成弹窗仍不等同于真实长期使用。

## 4. 最关键发现：请求者身份会劫持判断

研究在完全相同的 Calendar 任务下，只替换弹窗请求者：

| 弹窗请求者 | 四模型合计授权 |
|---|---:|
| Calendar | **26/32** |
| PiMusic | **0/32** |

![同一任务下请求者身份显著改变授权决策](/research-mobile/popup-assets/2608.04755/figure-2.png)

这不是普遍的“系统 App 崇拜”。换成 PiMusic 任务后，Calendar 请求者并未获得更多授权（9/32 对 12/32）。因此更准确的解释是：

**模型把“请求者看起来与任务有关”当成了权限必要性的替代证据。**

这是任务条件化的请求者身份偏差。它揭示了一条危险捷径：

```text
当前任务属于 Calendar
  → 弹窗也来自 Calendar
  → 模型推断“与任务有关”
  → 忽略具体权限是否必要
  → 倾向 Allow
```

各模型在 Calendar 与 PiMusic 请求者对照中的 Holm 校正 p 值分别为：Doubao、Gemini **6.22×10⁻⁴**，GPT **0.014**，Qwen **0.077**。Qwen 的单模型证据没有达到常用 0.05 阈值，不能把聚合趋势写成四个模型都显著。

## 5. 任务先验可以覆盖同一弹窗

作者固定弹窗内容，只更换任务上下文，授权率发生大幅翻转：

| 模型 | 无关任务 | 相关任务 |
|---|---:|---:|
| Doubao | 0 / 10 | 9 / 14 |
| Gemini | 6 / 9 | 14 / 14 |
| GPT-5 | 0 / 12 | 7 / 14 |
| Qwen3-VL | 0 / 10 | 13 / 14 |

通讯录场景也出现同样趋势：从 PiMusic 任务切换到 Contacts 任务后，四个模型分别由 0/11、5/11、4/11、0/11 上升到 14/15、15/15、8/15、12/15。

这表明 Agent 并非只读弹窗文本；任务先验会强烈参与决策。但问题也恰恰在这里：**任务相关性不等于当前权限的功能必要性。**

## 6. 提示词能否解决

论文比较原始提示、轻量安全提示和结构化安全提示：

| 模型 | L1：原始 → 轻量 → 结构化 | 风险授权：原始 → 轻量 → 结构化 |
|---|---|---|
| Gemini | 100 → 94 → 31.8 | 69.2 → 22.7 → 0 |
| Qwen3-VL | 95.5 → 92.6 → 52.9 | 56.1 → 18.2 → 1.5 |
| Doubao | 74.2 → 68.2 → 27.9 | 26.8 → 15.7 → 0.5 |
| GPT-5 | 67.6 → 34.9 → 16.2 | 25.6 → 2.6 → 0 |

![提示增强同时压低风险授权和必要授权](/research-mobile/popup-assets/2608.04755/table-3.png)

结构化提示几乎消除了风险授权，却让许多 L1 必要授权一起坍塌。作者进一步要求模型沿“权限 → 功能 → 当前任务”功能链推理：

- GPT-5：风险授权 25.6% → **0.5%**，L1 授权 67.6% → **30.9%**；
- Gemini：风险授权 69.2% → **3.5%**，L1 授权 100% → **70.1%**。

功能链比笼统的“谨慎一点”更有效，但仍未实现统一校准；GPT-5 在 Calendar 的 L1 授权只剩 **7.1%**。

## 7. 对移动 GUI Agent 的启示

一个可落地的权限决策器至少应拆成四层：

```text
任务语义
  → 当前步骤需要哪些功能
  → 功能最少需要哪些权限
  → 请求者与权限是否匹配
  → Allow / Deny / Defer
```

产品层面应把**任务执行**与**授权决策**分离：

1. 执行器提出“为了下一步，我需要什么能力”；
2. 授权层独立核对请求者、权限、作用域和时机；
3. 不确定时优先 Defer，而不是用任务完成压力替代判断；
4. 授权后验证功能是否真的需要并使用了该权限；
5. 评估同时报告 L1 召回与 L2–L4 风险授权，不能只报总拒绝率。

这套独立授权层是论文结果支持的设计方向，**不是论文已经实现并验证的系统**。

## 8. 如何正确解读

可以确认的是：

- 四种模型都表现出不同程度的过度授权；
- 请求者身份与任务上下文会系统性改变决策；
- 提示增强存在明显“安全—可用性”权衡；
- 权限评估必须同时测该允许和不该允许的场景。

不能据此宣称的是：

- 所有 GUI Agent 或所有操作系统都具有同样问题；
- 模型公开的思维链等于真实内部机制；
- 结构化提示已经解决权限安全；
- 论文提出的独立授权层已经完成工程验证。

研究局限包括：单一自动化框架、仅 Android、五个 App、合成弹窗注入、权限类型有限，以及没有覆盖长期自然流程、用户差异和权限累积效应。

## 9. 最终判断

这篇论文最有价值的地方，不是再次证明“模型会点错按钮”，而是识别出一种可复现的决策捷径：

> Agent 会把任务相关的请求者身份当成权限必要性的证据，并在完成任务的压力下过度 Allow。

因此，移动 GUI Agent 的安全目标应从“更保守”升级为“更会判断”：既能拒绝 L2–L4，也能稳定保留 L1。下一步最值得做的是把权限素养作为独立基准与策略层，使用真实弹窗、跨平台任务和长期权限状态继续验证。
